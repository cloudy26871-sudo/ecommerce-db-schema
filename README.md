# E-commerce Database Schema

Этот проект содержит пример схемы реляционной базы данных для интернет-магазина на PostgreSQL. В схеме предусмотрены сущности клиентов, категорий товаров, продуктов, заказов, позиций заказа, оплат и адресов.

## Содержимое

- `schema.sql` — основной SQL-скрипт с таблицами, связями, индексами, примером данных и view

## Схема базы данных

Основные таблицы:
- `categories` — категории товаров
- `customers` — клиенты
- `products` — товары
- `orders` — заказы
- `order_items` — позиции в заказе
- `payments` — платежи
- `addresses` — адреса клиентов

## Основные решения по проектированию

### 1. Использование `VARCHAR(n)`
Для полей с ограниченной длиной (например, `name`, `email`, `sku`, `slug`, `phone`) использован `VARCHAR(n)`, потому что:
- данные имеют естественный ограниченный размер;
- это позволяет контролировать допустимую длину;
- индексирование и хранение обычно эффективнее, чем для бесконечного текста;
- при этом поля остаются достаточно гибкими для бизнес-логики.

Пример:
- `email VARCHAR(255)` — стандартная длина почты и корректная валидация;
- `name VARCHAR(200)` — достаточная для наименования товара;
- `slug VARCHAR(120)` — обычно компактнее и формализованнее, чем `TEXT`.

### 2. Использование `TEXT`
Для больших текстовых описаний допустимо использовать `TEXT`, так как:
- описание товара может превышать стандартные ограничения;
- нет необходимости жёстко задавать длину;
- это удобно для детализации характеристик и карточек товара.

### 3. Использование `NUMERIC` для денежных значений
Для всех сумм (`price`, `cost_price`, `subtotal`, `total_amount`, `discount_amount`, `amount`) используется `NUMERIC(12,2)` или `NUMERIC(14,2)`, потому что:
- финансовые расчёты должны быть точными;
- `FLOAT` и `REAL` могут вносить ошибки округления;
- PostgreSQL `NUMERIC` хранит значения с фиксированной точностью.

### 4. Использование `TIMESTAMPTZ`
Для временных меток (`created_at`, `updated_at`, `paid_at`) используется `TIMESTAMPTZ`, поскольку:
- важно учитывать часовые пояса;
- это корректно для систем с несколькими регионами;
- такие метки обычно используются в аналитике и отчётах.

### 5. Использование `BIGINT` для идентификаторов
Для идентификаторов (`customer_id`, `product_id`, `order_id`, `payment_id`) применяются `BIGSERIAL` / `BIGINT`, потому что:
- интернет-магазин растёт быстро;
- может накапливаться большое количество записей;
- `INTEGER` со временем может исчерпаться;
- `BIGINT` даёт достаточный запас на рост.

### 6. Использование `ENUM`
Для статусов (`order_status`, `payment_status`, `payment_method`) используется `ENUM`, потому что:
- статусы ограничены заранее известным набором значений;
- это повышает целостность данных;
- упрощает фильтрацию и аналитические запросы.

## Представление (View)

В SQL-скрипте создано представление `ecommerce.customer_order_summary`.

Оно позволяет быстро получить сводку по заказам клиента с такими колонками:
- клиент
- номер заказа
- статус заказа
- сумма заказа
- количество товаров
- общее количество единиц

Пример запроса:

```sql
SELECT *
FROM ecommerce.customer_order_summary
ORDER BY customer_id, order_created_at;
```

## Партиционирование `orders`

Таблица `orders` подходит для партиционирования, потому что:
- она быстро растёт;
- многие запросы идут по диапазону дат;
- отчёты и ретроспектива по периодам обычно выполняются по времени.

### Рекомендуемый вариант
- Partition by RANGE на колонке `created_at`
- Разбивка по месяцам
- Пример: `orders_2026_10`, `orders_2026_11`, `orders_2026_12`, ...

Преимущества:
- уменьшение объёма сканируемых данных;
- быстрее запросы по периоду;
- проще управлять архивированием и удалением старых данных.

### Почему не ежедневно
Ежедневное партиционирование создаёт слишком много секций и увеличивает административную нагрузку. Для большого e-commerce проекта месячная гранулярность — практичный и сбалансированный вариант.
